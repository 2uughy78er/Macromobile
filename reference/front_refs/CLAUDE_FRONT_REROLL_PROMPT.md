# 컴프야 리세 앞부분 구현 지시서

## 목적
기존 Android 이미지 매크로 프로젝트에, 제공된 리세 영상에서 확인되는 "팀 선택 → 초반 진행 → 보상/메뉴 → 뽑기 진입 → 결과 화면" 앞부분을 이미지 기반으로 자동화한다.

## 기존 구현 보존
- 기존 MacroEngine / StepExecutor / TemplateMatcher / TARGET_CHECK / Accessibility / MediaProjection을 재사용한다.
- 기존 기능을 삭제하거나 전면 재작성하지 않는다.
- 좌표 고정 매크로를 새로 만들지 않는다. 가능한 모든 화면 전환과 버튼 클릭은 WAIT_FOR_IMAGE / WAIT_AND_TAP / TAP_IF_FOUND 등 이미지 감지를 우선한다.

## 중요: 결과 화면은 이미 구현됨
결과 화면 단계는 기존 작업을 그대로 유지한다.
WAIT_FOR_IMAGE(확인 버튼) → TARGET_CHECK → 목표가 아니면 WAIT_AND_TAP(확인 버튼)
목표카드가 확대 카드로 감지되면 확인 버튼을 누르기 전에 즉시 STOP_MACRO.

## 영상 자료
원본 리세 영상: 1728x1080, 약 158.59초.
이 폴더의 0s~125s JPG들은 영상에서 추출한 후보 기준 프레임이다. 이것들은 최종 템플릿으로 무조건 등록하지 말고, 실제 화면 전환과 버튼/메뉴의 안정적인 공통 영역을 분석하는 참고 자료로 사용한다.

## 후보 구간
- 0s: TEAM SELECT / 삼성 라이온즈 선택 화면
- 5s: 초반 선수/튜토리얼 화면
- 30s: 경기/초반 진행 화면
- 40s: 경기 종료/대화 또는 진행 팝업
- 45~60s: 선수/덱/보유 선수 관련 메뉴
- 65~75s: 미션/보상/스카우트 관련 메뉴
- 80~90s: 팀 메뉴/선수 관리/구성 화면
- 95s: 뽑기 진입 직전 화면
- 100~115s: 뽑기 연출 및 카드 결과
- 120~125s: 설정/입력/다음 진행 관련 화면

## 작업 방식
1. 위 후보 프레임을 시간순으로 분석한다.
2. 각 단계에서 다음 단계로 넘어가기 위해 실제로 필요한 버튼/아이콘/화면 상태를 찾는다.
3. 애니메이션 중간 프레임은 템플릿으로 사용하지 않는다.
4. 템플릿은 화면 크기 변화에 강한 작은 UI 요소를 우선 사용한다.
5. 버튼 템플릿에는 searchRegion을 설정해 다른 화면의 유사 UI 오검출을 줄인다.
6. 각 단계 timeout은 유한하게 둔다. 로딩이 긴 단계는 충분한 timeout을 주되 무한 대기는 금지한다.
7. 실패 시 기존 OnTimeout 정책(RESTART/SKIP/STOP)을 활용한다.
8. 화면 전환 후 바로 클릭하지 말고 WAIT_FOR_IMAGE로 다음 상태를 확인한다.
9. 가능하면 한 화면에서 여러 버튼을 연속 좌표 클릭하지 않는다.
10. 영상만으로 확실히 판단할 수 없는 단계는 추측해서 구현하지 말고 TODO로 남기며 로그를 남긴다.

## 리세 상태 흐름 목표
REROLL_START
→ TEAM_SELECT
→ TUTORIAL/INTRO
→ EARLY_PROGRESS
→ REWARD/CLAIM
→ PLAYER/MENU_NAVIGATION
→ SCOUT/GACHA_ENTRY
→ GACHA_EXECUTE
→ RESULT_SCREEN
→ TARGET_CHECK

TARGET_FOUND → 즉시 STOP
TARGET_NOT_FOUND → 확인 버튼 → 다음 리세 사이클

## 반드시 테스트할 것
- 각 단계가 이미지가 나타날 때만 진행되는지
- 로딩이 길어도 timeout 전에는 성급하게 다음 단계로 가지 않는지
- 잘못된 유사 버튼을 클릭하지 않는지
- 결과 화면에서 TARGET_CHECK가 확인 버튼보다 항상 먼저 실행되는지
- 목표카드가 아닌 카드에서는 멈추지 않는지
- 목표카드 발견 시 입력이 즉시 차단되는지
- 기존 매크로 기능에 회귀가 없는지

## 실기기 해상도
실기기 결과 화면은 2304x1440이며 기존 기준 화면의 정확한 1.5배 스케일이 확인되었다. 기존 CoordinateMapper를 유지한다.

## 완료 조건
앞부분의 확실한 단계들을 실제 이미지 템플릿 기반 MacroStep으로 구성하고, 결과 화면의 기존 TARGET_CHECK와 연결한다. 구현 후 단위 테스트 및 CI를 실행한다. 추측으로 만든 단계는 완료로 보고하지 않는다.
